One search, end to end

Exactly what happens between an agent typing a question and receiving an answer — every call, every algorithm, with the real numbers from a real run.

Everything below was captured from an actual query against encode/httpx (125 files, 1,991 symbols). No numbers are illustrative.

The scenario. An agent is working in a repository and needs to know what happens when redirects loop. Without an index it would grep, guess, and read whole files — about 26,000 tokens. Here it asks LeanVFS instead. 
leanvfs search "what raises TooManyRedirects" --limit 5

The path a query takes

1

The agent shells out cli.py :: main

No daemon, no server, no socket. The agent runs a command and reads stdout. This is the whole integration surface — anything with shell access can use it.

2

The index heals itself first cli.py :: _open_for_query

Before answering, LeanVFS brings the index up to date. An agent that edited a file a second ago must not be served the previous state.

Each discovered file is hashed and compared to the stored hash. This is the first row of the invalidation matrix: identical bytes mean the file is skipped entirely — no parse, no writes, no work.

measured, 125 files, nothing changed
hash_skips = 125 parse_full = 0 90 ms total process time
measured, one file edited
reparsed = 1 skipped = 124 109 ms

If the index does not exist yet, it is built here — the agent never has to remember a setup step, and never sees an empty result that means "not indexed" rather than "no matches".

3

The query is decomposed search.py :: query_terms

Words are lowercased, then each is also split on camelCase, PascalCase, snake_case and kebab-case. Both the whole token and its parts are kept.

input
"what raises TooManyRedirects"
terms
['what', 'raises', 'toomanyredirects', 'too', 'many', 'redirects']

This one step is why an intent-phrased question can reach a symbol whose name it never literally contains: splitting TooManyRedirects into too, many, redirects lets the plain-English phrasing "too many redirects error after several hops" match the same symbol.

4

A candidate set comes out of FTS5 store.py :: fts_search

Terms become an OR-of-prefix expression. Every term is quoted, so punctuation in a user's question can never be parsed as FTS syntax — that is both a correctness and an injection concern.

match expression
"what"* OR "raises"* OR "toomanyredirects"* OR "too"* OR "many"* OR "redirects"*
returned
362 candidates, ranked by SQLite's BM25 a few ms

BM25 alone is a weak ranking for code — it knows nothing about symbols, paths or file roles. It is used only to narrow the field cheaply; the real ranking is next.

5

Re-ranking: the part that decides the answer search.py :: SearchEngine.search

Each candidate starts from its BM25 score and accumulates structural evidence. Every weight is config, not code — this is the surface the benchmark optimises over.

score  = bm25            × 1.0
       + exact_symbol    × 4.0    # the symbol name IS a query term
       + symbol_parts    × 4.0 × (overlap / parts)
       + qualified_symbol× 3.0 × 0.5
       + path            × 1.2 × (overlap / parts)
       + keyword         × 1.0 × (matching indexed keywords)

score ×= class_source 1.0 | class_tests 0.8 | class_docs 0.7

The final multiplier encodes an editorial judgement: when a question matches both an implementation and its test, show the implementation first — but keep the test, because a test is often the clearest statement of intended behaviour.

6

Diversification search.py :: _diversify

At most 3 hits per file; the surplus is demoted, not dropped. This came from a measurement, not a hunch: in the top ten, ripgrep returns 10.0 distinct files while a plain AST index returns 3.9. A list concentrated in one file covers less of a multi-file answer for the same tokens. Worth +1% nDCG@10 at cap 3.

7

A total order, so results never wobble Hit.sort_key

(-score, path, stable_key, doc_kind, doc_id)

Ties break on stable_key — never on SQLite's rowid, which depends on insertion order and would make identical queries return different orderings after a reindex. This is what lets the benchmark assert exactly zero variance across ten repetitions.

Step 9 — going deeper without opening the file

The agent now wants the contract of one symbol. get_context is the operation most responsible for the headline metric, so it is assembled by policy rather than from a fixed field list.

leanvfs context "Client._send_handling_redirects"

The admission algorithm budget.py :: admit

1. sort by (priority asc, confidence desc, kind asc, value asc)   # a total order
2. greedily admit while cumulative_tokens + cost(fact) <= budget
3. within a kind, respect per-kind caps BEFORE the global budget
4. record every dropped fact as (kind, priority, count, tokens_would_have_cost)
5. emit a budget_report alongside the payload

Identity, location and signature are unconditional — never subject to the budget. Everything else competes in a configured order: exceptions → side effects → invariants → test expectations → resolved calls → doc refs → keywords. Never the implementation body.

The agent now knows the signature, the return type, what it raises, what it calls, and that it touches the filesystem — without reading a single line of the 36-line body, let alone the 1,700-line file it lives in.

Why the drop record is not optional

When the budget bites, dropped reports exactly what was withheld and what it would have cost. An agent that cannot tell it received a partial answer does not know to ask for more, and a benchmark cannot tell a good policy from a lucky one. Silent truncation is a correctness bug, not a saving.

When it goes wrong

A walkthrough that only shows the good case is a sales demo. Here is the same pipeline on a question phrased entirely in plain English, with none of the codebase's vocabulary:

query
"what happens when a request keeps redirecting forever"
terms
['what', 'happens', 'when', 'a', 'request', 'keeps', 'redirecting', 'forever']
top results — wrong
11.80 httpx/_exceptions.py RequestError 9.26 httpx/_exceptions.py HTTPError.request 9.22 httpx/_models.py Response.request 9.19 httpx/_exceptions.py HTTPError.request

TooManyRedirects does not appear at all. The common word "request" dominates the score, and redirecting never stems to redirects — there is no stemmer in the pipeline. The failure is total, not partial.

This is measured, not anecdotal: across the benchmark suite, 18 of 50 intent-phrased probes score exactly zero. The obvious fix — a query-side stoplist plus IDF weighting — was implemented and measured worse (nDCG@10 0.335 → 0.317), so it was reverted and kept as default-off config. The honest state is that this is the system's largest known weakness and the fix is not yet known.

What this means for an agent

Phrase queries with the vocabulary you expect the code to use. "TooManyRedirects", "redirect limit" and "max_redirects" all work; "keeps redirecting forever" does not. The system is a strong lexical-structural matcher, not a semantic one — there are no embeddings anywhere in it, by design.
