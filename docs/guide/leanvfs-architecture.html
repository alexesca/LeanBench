LeanVFS

A local, offline, deterministic semantic projection of a repository — so a coding agent can find what it needs without reading whole files.

One objective, and everything below is downstream of it: maximise software-engineering usefulness per repository token consumed. The real repository stays authoritative. LeanVFS is a projection of it, not a compression of it.

1 · The idea in one page

An agent asked “where does this codebase decide to follow a redirect?” has two options. It can read files until it finds out — which is accurate and enormously expensive — or it can consult an index. Most indexes answer with locations. LeanVFS answers with compressed meaning, and only then points at source.

search LeanVFS→ identify symbols & files→ inspect tests, docs, relationships→ open only necessary real source

The last step is the point. Every design decision below exists to make the agent's final read small and correct, rather than to make the index clever.

Ten invariants, each enforced by a test named after it

1Source is authoritative — LeanVFS never modifies repository content
2Generated state is disposable — delete .leanvfs/, re-sync, get equivalent state
3Incremental converges to clean, at the same idf_generation
4Bounded work per edit — O(changed file + resolution fan-in), never O(repo)
5Secrets never persist — one redaction choke point, no second path
6No rewrite cascades — reverse edges are queried, never materialised
7Deterministic — identical bytes at 1, 4 or 16 workers
8Config-driven — no consequential parameter is a Python constant
9Parsers emit canonical facts, never presentation
10Staleness is visible — never silently stale

2 · The pipeline

discover→ classify→ hash→ parse / extract→ canonical model→ resolve relationships→ priority & budget→ SQLite + FTS5→ query engine

Where parallelism is allowed, and where it is forbidden

Files are parsed in parallel. Everything ordering-sensitive is sequential and index-ordered. Extractions are buffered per file, merged in sorted path order, and only then assigned ids. Sort keys are total; no dict or set iteration reaches output. A test indexes the same repository at 1, 4 and 16 workers and asserts the canonical state is byte-identical.

This ordering discipline is why determinism was built in at the canonical-model stage rather than retrofitted. Retrofitting it later is far more expensive, because by then every extractor has quietly baked in an assumption about arrival order.

3 · The canonical model

Parsers emit facts, never rendered text. Rendering, indexing and serving all consume the canonical model separately — which is what makes format experiments cheap, and format is one of the highest-value things to experiment with.

Stable identity

python:src/auth/service.py:method:
  AuthService.login(email,password)

Language, repo-relative path, kind, qualified name, and a discriminator built from parameter names only — so adding a type annotation does not reassign identity. Never line-dependent.

Fact-kind registry

Every fact kind declares its value grammar, cardinality and default priority. Extractors emit through the registry, and an unregistered kind is a hard error, not a warning.

Stringly-typed values rot without this. The registry is the discipline that stops it.

4 · The invalidation matrix

Four hashes per symbol. Each one gates specific work — that is what makes them load-bearing rather than decorative.

ConditionAction
source_hash unchangedSkip the file entirely. No parse, no writes.
source_hash changed, structure_hash unchangedFormatting or comment movement only. Update line offsets. No fact recomputation, no re-resolution.
interface_hash changedRecompute signature facts; mark inbound edges for re-resolution — callers may no longer match.
behavior_hash changedRecompute call, effect, exception and keyword facts; re-resolve this symbol's outbound edges only.
doc_hash changedDoc and comment facts only.
metadata_hash changedDecorator and attribute facts only.
Symbol absent from the new parseDelete it; demote inbound edges to unresolved.

Measured on httpx: a one-line edit reparses 1 file and skips 124, end to end in 69.7 ms against a full sync of 1,105 ms.

5 · Relationship resolution

This is the hardest subsystem, and it is deliberately not a side effect of parsing. Resolving repo.find_by_email to a real symbol without a type checker is the accuracy problem in this project.

Two phases. Phase A runs per file, in parallel, and emits unresolved references — raw target text plus syntactic hints. Phase B runs once, sequentially, after every file is parsed, against the complete symbol table. A reference cannot be resolved against a symbol table that is still being built.

R4 edges are still emitted. “Calls something named stripe.charge” is useful even unresolved. A reference is never dropped for being unresolvable.

The trap that silently breaks incremental correctness

Adding a file can resolve references that were dangling elsewhere; deleting one dangles references that were resolved. A pipeline that only touches the changed file corrupts the graph without any error. LeanVFS keeps an unresolved_refs table indexed on name, and on deletion re-resolves exactly the referring files — a bounded fan-in lookup, never a repository scan.

6 · The budget engine

This is where the product thesis is actually enforced, so it gets an algorithm rather than a list of knobs.

1. sort by (priority asc, confidence desc, kind asc, value asc)   # total order
2. greedily admit while cumulative_tokens + cost(fact) <= budget
3. within a kind, respect per-kind caps BEFORE the global budget
4. record every dropped fact as (kind, priority, count, tokens_would_have_cost)
5. emit a budget_report alongside the payload

The drop record is not optional. “You spent 34% of the file budget on keywords and dropped 12 test expectations” is the signal needed to reallocate the budget. A truncation the caller cannot see is a correctness bug, not a saving.

The money operation

get_context is assembled by policy, not from a fixed field list. Identity, location and signature are unconditional. Everything else competes for the remainder in a configured order: exceptions → side effects → invariants → test expectations → resolved calls → doc refs → keywords. Never the implementation body. The assembly order is config, because it is one of the most valuable things to tune.

7 · The frozen-statistics rule

The most expensive latent bug in the original design

Keyword scores were specified as structural weight × repository-wide IDF. But repository-wide IDF is a global statistic: editing one file shifts document frequencies, which changes keyword selection in unrelated files. So either incremental state diverges from a clean rebuild (breaking invariant 3), or every edit reparses the repository (breaking invariant 4). Both cannot hold.

Resolution: IDF is a versioned snapshot. It is computed during a full sync, frozen under an idf_generation, and incremental updates read it and never write it. Equivalence is then defined against a rebuild at the same generation, which makes invariant 3 both true and testable.

The mechanism is a capability token: compute_idf() requires a GlobalStatsPermit, and full_sync() is the only function that mints one. An incremental path structurally cannot recompute a corpus statistic — it is not a convention to remember, it is a type error.

The rule generalises: no global statistic may be read during an incremental update unless it is generation-frozen. Any future corpus-wide signal — call frequency, symbol popularity, path priors — gets the same treatment.

8 · Secrets: a choke point, not a policy

“Secrets never persist” needs a mechanism. Every fact value passes through exactly one redact() function before it can reach SQLite, and the fact-insert API is private and accepts only a Redacted wrapper. There is no second path to forget about.

The identifier is kept; the value never is. STRIPE_API_KEY survives as a name; its contents become <redacted>. The test injects fake keys, JWTs, PEM blocks and connection strings, then scans every text column of every table, the FTS index, the rendered output and the protocol responses. It may not be skipped.

9 · The protocol surface

The benchmark's entire view of LeanVFS is JSONL over stdin/stdout. stdout carries protocol traffic and nothing else; all diagnostics go to stderr. A stray print() is classified as a protocol error — which is the correct outcome.

{"id":"2","op":"search","args":{"query":"redirect handling","limit":10},
 "token_budget":800,"format":"compact"}

{"id":"2","status":"ok","result":{...},
 "meta":{"tokens_approx":742,"truncated":true,"dropped":{"keyword":11},
         "index_state":"ok","generation":184,"idf_generation":12}}

index_state is how “wrong because stale” is distinguished from “wrong because the index is bad” — a distinction that otherwise costs many confusing debugging sessions. truncated must be honest: an agent that cannot tell it received a partial answer does not know to ask for more.

The compact format

Default output is line-oriented and low-punctuation, not JSON. A JSON envelope for the same content costs roughly twice the tokens, almost all of it structural noise.

@lvfs 1
@file src/auth/auth_service.py
lang=python class=source lines=612
imports.local=models.User,repositories.UserRepo
exports=AuthService,InvalidCredentials,AccountLocked

  fn login(email:str,password:str)->TokenPair async L47-128
    kw=login,password,user,jwt
    call=repo.find_by_email,password.verify,tokens.issue
    fx=db:r,crypto
    throws=InvalidCredentials,AccountLocked
    note[security]=locked users must never receive tokens

10 · How the architecture evolved

Six things changed after the design met measurement. Three were bugs the benchmark found that code review had not; two were my own design priors being overturned; one was a hypothesis that failed and was kept anyway as a recorded negative result.

Rust → Python reversed

The design argued Rust was load-bearing for an indexer: parse throughput, memory, cold start. True in principle. But nothing about token efficiency is language-dependent — it is decided by the canonical model, resolution accuracy, the priority ladder and the renderer. Building in Rust first meant paying a toolchain cost before learning whether the design saved any tokens at all.

Python, with a measured re-entry criterion: port when the design passes its gates and misses the latency budget for interpreter-bound reasons. Cold index currently runs at 3,235 KB/s against a 400 KB/s floor.

IDF made a frozen snapshot design fix

Three stated invariants were mutually contradictory (§7). Rather than quietly dropping one, IDF became generation-frozen and equivalence was redefined against a rebuild at the same generation. The permit token turned the rule from a convention into something the type system enforces.

Caught by reading the spec against itself, before any code existed.

On-disk mirror switched off by default deferred

The original design materialised a .lvfs text tree on disk, atomically rewritten on every edit. That is a second consistency domain — its own staleness bugs, write amplification and golden tests — serving a consumer that did not yet exist.

Rendering is now on-demand from SQLite, with a test asserting the two paths are byte-identical. Grep-over-projection stays a flag, to be earned by an experiment rather than assumed.

Query-side stoplist + IDF weighting failed, kept as config

18 of 50 intent-phrased probes were scoring exactly zero. Diagnosis looked conclusive: query terms were not normalised the way indexed terms were, so a natural-language question was scored mostly on its filler — one result was literally a docs theme colour matching on the word “media”. Symmetric normalisation is the textbook fix.

It measured worse. nDCG@10 fell from 0.335 to 0.317.

Reverted to what measured best. The knobs survive as default-off config, because “we tried it and it lost” is a result worth being able to re-run.

Builtin call suppression prior overturned

Two bugs in one place. The adapter policy was built from a single config section, so every calls.* key fell back to an inline default — builtin suppression had never run. Every lookup carried a default, so nothing failed; it just quietly behaved differently. This is precisely the failure mode “config over constants” is meant to prevent.

With suppression finally working, retrieval got worse. The design's assumption that str, len and isinstance were noise was wrong: they are lexical surface worth +1.3% nDCG@10, at zero cost in agent-visible tokens.

Default flipped to record them, with the measurement written beside the setting.

Symbol ids preserved across re-parse bug found by equivalence check

Incremental sync cleared a changed file's derived rows — including its symbol rows. Re-inserting gave every symbol a fresh id while edges from other files still referenced the old one. A one-file edit silently dangled inbound relationships across the repository, with no error anywhere.

Symbols are now upserted on stable_key — which is exactly why identity was defined to be line-independent — and only genuinely vanished symbols are pruned. Found by leanvfs verify, not by review.

Result diversification added +1% nDCG

Measured, not guessed: in the top ten results, ripgrep returns 10.0 distinct files; LeanVFS returned 5.1 and a plain AST index 3.9. Symbol indexes spend their top-k on redundant same-file hits, which covers less of a multi-file answer for the same tokens.

Cap hits per file, demote the surplus rather than dropping it. Swept 0/1/2/3/5/8 — three is best.

12 · What is still wrong

Reported because a system description that only lists its wins is an advertisement.

missed Call resolution

R0+R1 is 20.5% of CALLS edges against a 60% design target. The high-confidence tiers are thin; most edges land in R2/R3. This is the largest known lever on retrieval quality and it has not been pulled.

missed Index size

3.96× source bytes against a 1.5× ceiling. A system metric rather than an agent-token cost, but well outside budget.

weakness Paraphrase brittleness

LeanVFS has the best average retrieval score and one of the weaker worst cases across the three paraphrases. ripgrep degrades more gracefully when the question is phrased unlike the code.

unmeasured No LLM has been run

The agent track is driven by deterministic policies. The model-backed harness and its replay cache are not built, so no figure here is an LLM result.
